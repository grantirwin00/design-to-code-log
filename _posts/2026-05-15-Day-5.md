# Day 5: Craft Goes Cross-Department

Craft started as a Design tool. It's now a four-department platform. Design, Sales, Engineering, and Product -- each with five learning buckets, curated resources, step-by-step learning paths, and opinionated recommended approach items written to match the tone and specificity of the original Design content. 22 buckets total, up from seven. All in a single build push.

---

## Data Structure Migration

The foundational change was structural. The flat bucket list that powered the original single-department app was migrated to a nested shape organized by department. Both the live `data.json` and the hardcoded fallback data inside the app were updated to match. Everything downstream -- rendering, the CMS, routing -- had to be updated to consume the new shape.

The recommended approach items across the new departments were written to be specific and opinionated rather than generic. "Role-play the close before every high-stakes deal" for Sales. "Treat flaky tests as bugs" for Engineering. The same energy as the original Design content, applied to each department's actual working context.

---

## Hash-Based Routing

Navigation got a full overhaul. The app now uses hash-based routing -- `#/design`, `#/sales`, `#/engineering`, `#/product` -- so every department and every bucket detail page has a real, shareable URL. A fixed department tab bar sits just below the main nav, letting users switch departments from anywhere in the app.

On bucket detail pages, the full top nav stays visible and the back button lives in a secondary strip below it, using the same visual language as the department tabs. The hierarchy is clear without adding more navigation layers.

The admin CMS panel got its own tab switcher that filters the bucket list by department and scopes all edits -- add, edit, delete -- to whichever department is active.

---

## Admin Access Rework

The original `?admin` URL pattern was replaced with a "CMS Admin" button that lives in the top nav on every public page. Clicking it opens a login modal overlay without leaving the page or changing the URL. After authenticating, the user lands directly in the admin dashboard. Both "View Craft" and "Sign Out" return to the public home.

If a session is already authenticated, the button label changes to "Admin" and skips the login step entirely. It's a small detail that makes repeated admin sessions feel less clunky.

---

## Bug Fixes

Two bugs surfaced after the first merge to production.

**White screen on load.** Users who had visited the old single-department version had data cached in `localStorage` in the old flat-array format. The new code tried to call `.departments.map()` on that array, crashed immediately, and rendered nothing. The fix was a one-line shape check in `getFullData()` that falls back to default data if the cached value doesn't have the expected structure. Classic migration problem -- the cache knows what the old app taught it.

**Routing race condition.** On first load, the page was rendering before the data fetch resolved, using hardcoded defaults instead of the live `data.json`. A `_dataReady` flag now gates all hash-change-triggered renders until after data is loaded.

---

## Other Details

- Added `package.json` with `"type": "module"` to stop Vercel from transpiling the serverless function from ESM to CommonJS
- Increased hero section top padding to create more breathing room between the department tabs and the page title
- Updated the CMS publish function to send the full four-department data shape instead of a single department's bucket list

---

## What I Learned

Data shape changes are the riskiest kind of migration. The white screen bug was entirely predictable in hindsight -- any time you reshape a data structure that's been persisted to a client-side cache, you have to assume the old shape is out there and write a fallback. The fix was one line, but catching it required understanding the full lifecycle of where that data lives and who reads it.

The routing race condition is the same lesson from a different angle: don't trust that async operations will resolve before the UI tries to use their output. Gate the render. Make the dependency explicit.
